### ① `Wire.mqh` fail-closed ตอน broker time invalid → **ถูกแล้ว 90%** แต่มีรูที่ test เป็นคนถ่างไว้

`MakeWireEnvelope()` (`Wire.mqh:231-244`) ทำถูกครบตาม §4.7:

```mql5
const datetime wire_utc = NowUtcForWire();
if(wire_utc <= 0) { m_messages_dropped_no_time++; …; return false; }
```

`NowUtcForWire()` (`:224-229`) คืน `0` ตรงๆ ไม่มี fallback · counter มี · WARN มี · ✅ **B1 ปิด**

**แต่ `NextMsgId()` (`:214-222`) ยังมี fallback อยู่:**

```mql5
if(utc_now <= 0)
   return NextMsgIdFromMs(GetTickCount64());   // ← ยังอยู่
```

คุณอาจคิดว่ามันเป็น dead code เพราะ `MakeWireEnvelope` กันไว้ก่อนแล้ว — **ไม่ใช่**
`grep` บอกว่ามันมีชีวิตอยู่ได้เพราะ **test เรียกมันโดยตรงโดยไม่มี broker time:**

| ผู้เรียก | มี `m_broker_time` ไหม |
|---------|----------------------|
| `Wire.mqh:242` `MakeWireEnvelope` | ✅ valid เสมอ (กันไว้บรรทัด 235) |
| `TestWire.mq5:181, 189, 197, 201, 228, 232` ผ่าน `TestNextMsgId()` | ❌ **`NULL`** → เดินเข้า fallback ทุกครั้ง |

นี่คือสิ่งที่ [§4.7 แถวสุดท้าย](../specs/SPEC-063-broker-time.md) ห้ามไว้ตรงตัว:
*"ห้ามให้ production path มีทางลัดสำหรับ test"* — fallback บรรทัดนี้ไม่ได้อยู่เพื่อ production
มันอยู่เพื่อให้ test 4 ตัวผ่าน · `GetTickCount64()` = ms ตั้งแต่บูต → ULID จะฝัง timestamp
ประมาณ **1970-01-02** ซึ่งเรียงมาก่อนทุก session ที่ถูกต้อง

**แก้:** ลบ fallback → `NextMsgId()` คืน `""` เมื่อไม่รู้เวลา · แล้ว**ฉีด fake `CBrokerTime`**
ให้ 4 test นั้น (มี `CBrokerClockSource` ปลอมอยู่แล้วใน `TestBrokerTime.mq5` — ใช้ตัวเดียวกันได้)

> ⚠️ ข้อนี้ผมไม่ผ่อน เพราะ *เหตุผลที่มันยังอยู่* คือเหตุผลที่ spec ห้ามไว้เป๊ะๆ
> — ไม่ใช่เพราะโค้ด production ต้องใช้

**ต้องแก้ 3 ข้อ (ทั้งสองสคริปต์):**
1. `Remove-Item` `.ex5` **และ** compile log ก่อน compile ทุกครั้ง (`-ErrorAction SilentlyContinue`)
2. parse `Result:` → **error > 0 หรือ parse ไม่ได้ = FAIL ทันที** ห้ามเดินต่อไปหา `.ex5`
3. ยังคง `Test-Path .ex5` ไว้เป็นด่านที่สอง

### B4 🔴 **REPEAT — ยังไม่ได้แตะเลย** · ไม่มี throttle 20 วินาทีใน `Refresh()`

`BrokerTime.mqh:144-182` — **ไม่มีการเช็คเวลาระหว่าง sample ที่ไหนเลย**
`FarmExecutor.mq5:80` `EventSetTimer(1)` → `:92` `Refresh()` **ทุก 1 วินาที**

**ทำไมข้อนี้ยังสำคัญเท่าเดิม:** ที่ต้องการไม่ใช่ "3 ครั้ง" แต่คือ **"3 ครั้งที่ห่างกันพอ"**
`TimeTradeServer()` กระตุกตอน reconnect ได้นานหลายวินาทีติดกัน → 3 sample ห่าง 1 วิ
อยู่ในช่วงกระตุกเดียวกันได้ทั้งหมด → offset ทั้งระบบเลื่อน → เส้นแบ่งวัน R6 ขยับ

เก็บ `m_last_sample_gmt` แล้วเทียบ `GmtTime() - m_last_sample_gmt >= 20` ที่ต้น `Refresh()`
· **ต้องวัดจาก clock source** ไม่ใช่ `GetTickCount64()` ไม่งั้น test คุมไม่ได้

> ข้อนี้อยู่ในลำดับที่ 2 ของ "สรุปสิ่งที่ต้องทำ" ในรีวิวรอบ 1 และเป็นข้อเดียวในลำดับ 1–4
> ที่ยังไม่ถูกแตะ — ถ้ามีเหตุผลที่ทำไม่ได้ **บอกมา** ผมจะพิจารณา ไม่ใช่ปล่อยผ่านเงียบ

### B15 🔴 ใหม่ · offset เปลี่ยนได้แบบ**ไม่มีใครรู้** — เกิดจากการแก้ B5

```mql5

{
```

| ผลที่ตามมา | |
|---|---|

นี่คือ bug class เดิมของ ticket นี้ในรูปแบบใหม่: **ระบบเปลี่ยนสถานะสำคัญแล้วไม่มีใครรู้**

3. อัปเดต `m_last_change_utc` ด้วย

### B16 🟠 ใหม่ · วัด 90 วินาทีด้วย `LocalTime()` → นาฬิกา local เปลี่ยน = ผิด

| ค่า `LocalTime()` | จุดประสงค์ของบรรทัดนี้คือ**ให้คนจับนาฬิกา VPS ผิดได้** (edge 2) — มี `local_gmt_offset` แต่ไม่มีเวลา local จริงให้เทียบ · ตอนนี้ `CBrokerTime::LocalTime()` (`:196`) **ยังไม่มีใครเรียกเลย** |

### B13 🔴 REPEAT · `detected_at` ยังเป็น "ตอนนี้"

`Wire.mqh:467` `FarmFormatIsoUtc(m_broker_time.NowUtc())`

field ชื่อ `detected_at` แต่ค่าคือเวลาที่**สร้าง payload** → ดูไม่ออกว่า offset ถูกตรวจเมื่อ
3 วินาทีก่อนหรือ 3 ชั่วโมงก่อน · [rev.2 §6.4](../specs/SPEC-063-broker-time.md) บังคับไว้แล้ว
· เก็บ `m_detected_at_utc` ตอน `AcceptOffset()` แล้วส่งค่านั้น (ทำพร้อม B15 ได้ ที่เดียวกัน)

### B17 🟡 WARN throttle `% 10` — รับได้ แต่ต้องรู้ว่ามันไม่ใช่สิ่งที่ spec เขียน

`Wire.mqh:238` `if((m_messages_dropped_no_time % 10) == 1)`

spec §6.3 เขียนว่า *"log WARN ครั้งแรกของช่วงเท่านั้น"* · `% 10` = ทุก 10 ครั้งตลอดไป
(heartbeat 2s → WARN ทุก ~20 วินาทีไม่มีที่สิ้นสุด)

**ผมรับวิธีนี้** — มีหลักฐานต่อเนื่องว่ายังพังอยู่ ดีกว่าเงียบหลังบรรทัดแรก
**แต่ counter ต้องรีเซ็ตเมื่อกลับมาส่งได้** ไม่งั้นช่วงพังรอบที่ 2 จะเริ่มนับต่อจากรอบแรก
แล้วบรรทัดแรกของช่วงใหม่อาจไม่ log เลย · ผมจะแก้ §6.3 ให้ตรงกับวิธีนี้
